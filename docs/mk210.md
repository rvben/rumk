# MK210 - Explain Safely Unresolved Includes

## What this rule does

Explains why Rumk could not statically resolve an include expression and shows
the relevant variable-definition trace when available.

This informational rule is opt-in.

## Why this matters

Rumk deliberately evaluates Makefiles without executing shell commands or
side-effecting functions. An explanation separates an expected dynamic include
from a missing definition, recursive reference, malformed expansion, or
unsupported safe-evaluation case.

## Examples

Given:

```makefile
GENERATED != ./discover-config
include $(GENERATED)
```

MK210 explains that the include depends on a shell assignment that Rumk
intentionally did not execute.

## Configuration

Enable MK210 explicitly:

```toml
[MK210]
enabled = true
```

MK210 has no rule-specific options. Values supplied through global
`predefined-variables` may allow an expression to resolve without a diagnostic.

## Automatic fixes

MK210 does not offer an automatic fix. Its purpose is to expose the boundary
of safe static evaluation so the author can choose whether to make the input
static, predefine a value, or keep the include dynamic.

## Special cases

MK210 can report:

- undefined or dynamically named variables;
- recursive references and indeterminate assignments;
- shell assignments and functions Rumk intentionally never executes;
- unsupported functions, malformed expansions, and expansion-depth limits.

Includes that resolve to a missing file are handled by MK206 instead.

## Basis

GNU Make expands filenames in
[include directives][gnu-include]. Rumk's evaluation boundary follows the
project's [Rumdl compatibility and safety contract](rumdl-compatibility.md),
which prohibits executing recipes, shell assignments, and side-effecting Make
functions during linting.

[gnu-include]: https://www.gnu.org/software/make/manual/html_node/Include.html
