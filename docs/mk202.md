# MK202 - Avoid Hardcoded Absolute Paths

## What this rule does

Reports absolute POSIX and Windows paths in variable values and recipes.

This rule is opt-in.

## Why this matters

Absolute paths tie a Makefile to one machine, operating system, or directory
layout. Variables and paths relative to the project are easier to override in
local development, CI, packaging, and cross-platform builds.

## Examples

### Correct

```makefile
INSTALL_ROOT ?= $(DESTDIR)

install:
	cp app $(INSTALL_ROOT)/bin/app
```

### Incorrect

```makefile
INSTALL_ROOT := /opt/example

install:
	cp app /usr/local/bin/app
```

## Configuration

Enable MK202 explicitly:

```toml
[MK202]
enabled = true
```

MK202 has no rule-specific options.

## Automatic fixes

MK202 does not offer an automatic fix. Rumk cannot know which project
variable or relative location expresses the author's intent.

## Special cases

- POSIX paths begin with `/`; tokens beginning with `//` are ignored.
- Windows paths use a drive-letter form such as `C:\\tools`.
- Detection is token-based. Paths assembled from Make variables are not
  reported as hardcoded source text.

## Basis

MK202 is a Rumk portability convention, not a GNU Make syntax requirement.
It is opt-in because absolute paths can be intentional in controlled build
environments.
