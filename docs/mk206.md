# MK206 - Resolve Required Includes

## What this rule does

Reports required, statically evaluable Makefile includes that cannot be found,
read, or parsed.

## Why this matters

A required include is part of the build definition. Missing or invalid input
can stop Make before it considers any target, while a generated include may
indicate that the build graph needs to explain how that file is remade.

## Examples

### Correct

```makefile
include config/common.mk
-include config/local.mk
```

### Incorrect

```makefile
include config/does-not-exist.mk
```

An include is also incorrect when it is read before the variables it names have
a value. GNU Make expands such a reference to nothing, so this reads
`/common.mk` rather than `config/common.mk`:

```makefile
include $(CONFIG_DIR)/common.mk
CONFIG_DIR := config
```

## Configuration

MK206 is enabled by default and has no rule-specific options. Configure
additional GNU Make-style include search directories globally:

```toml
[global]
include-paths = ["mk", "vendor/build"]
```

Relative entries are resolved from the directory containing the Rumk
configuration file.

## Automatic fixes

MK206 does not offer an automatic fix. A missing include might need to be
created, generated, made optional, or found through another search path.

## Special cases

- `-include` and `sinclude` are optional and are not reported when absent.
- An include that is not valid UTF-8 is read as GNU Make reads it, as bytes,
  and is analyzed with the invalid sequences replaced; MK007 reports how it is
  encoded when that file is checked.
- A missing include that is also a known build target is treated as generated.
  A pattern rule counts as one of those, since Make remakes a makefile through
  `%.mk: %.mk.in` or even `%:` as readily as through a rule naming the file. It
  counts only where the pattern carries a recipe and everything it asks for is
  either on disk or something Make can make: Make passes over a pattern whose
  prerequisites it can neither find nor make, and then says the file has no rule
  at all. What a pattern asks for may be the work of another pattern, and Make
  chains them, so this follows the chain. Make refuses to use one pattern rule
  twice along a single chain, which is where the search ends: `%X: %XX` builds
  `aX` from an `aXX` on disk, but not from an `aXXX`, and neither does Rumk read
  it that way. Two more limits shorten a chain, and Rumk reads both. A rule
  written with `::` is terminal, so what it asks for has to be on disk or have a
  rule of its own; Make will not reach it through another pattern rule. And a
  rule whose target is `%` alone is not used for a name Make reached only by
  working backwards from another pattern rule, unless it too is written with
  `::`, so `%: %.src` remakes an included `config.mk` but supplies nothing to
  `%.mk: %.mid`. Writing `all: config.mid` somewhere makes `config.mid` a file
  Make was told about rather than one it invented along the way, and the `%`
  rule builds it again. A static pattern rule says it just as plainly, because
  Make fills its target's stem into what it asks for as it reads the line, even
  where the pattern itself is written as a variable, and so does an `include`,
  required or optional, since Make has a file of its own for everything it is
  told to read. Each of these names is read the way Make files it, without the
  leading `./` it may be written with. Where one of them is written so that
  Rumk cannot read it at all, such as an include named through `$(shell ...)`,
  the file Make was told about may be the very one the chain needs, so nothing
  is reported about that include.
- An include whose expression names a variable that has no value where Make
  reads it, and that the project defines somewhere Make has not read yet, is an
  error, and the message names the line or file that defines it. Make reads the
  expression with that reference contributing nothing, whether that means a
  different file, no file at all, or a file it cannot find. A definition Make
  read and gave back with `undefine` is one it has read, so the message names
  the definition after it rather than that one.
- A `:=` assignment is read as the reading it was, so this holds for a variable
  computed from a name that had no value yet, and the message names the name
  behind it. The definition that arrives too late is the one after that
  assignment, which may still be above the include: what the variable holds was
  settled where it was written, so Make reads a file that definition was never
  part of.
- An include whose expression names a variable that has no value there, with no
  definition of it still to come, is reported as a warning, and only where Make
  then finds no file to read. That covers a name given a value and taken back
  with `undefine` and never given another, one defined only in a branch Make
  does not take, and one only a rule carries, which Make holds long after it
  reads the include.
- A name the project gives no value of its own is not reported at all: a caller
  supplies it through the environment, the command line or a parent make, none
  of which Rumk reads, and a fragment written to be included that way reads
  exactly like a mistake. A definition that only reads the name back and writes
  it again, such as `NDK_ROOT := $(strip $(NDK_ROOT))`, gives no value of its
  own either. Opt-in MK208 is where these are reported. Giving the name a value
  under `[global] predefined-variables` makes Rumk resolve the include the way
  that value does.
- Nothing about a variable's value is said below an include Rumk could not
  read, whether its path came out of `$(wildcard ...)` or `$(shell ...)`, the
  file itself could not be opened, it stood past the project file limit, or it
  stood under a condition Make decides while it reads. Make may read that file
  and hold whatever it defines; Rumk does not, so a name that reads as having no
  value there may have had one all along, and a definition below it may be the
  `?=` that never happens. An include above such a file is still reported in
  full, and so is one below an include Rumk can name every file for and finds
  none of them, since Make took nothing from that either way.
- Nothing about a variable's value is said below a missing include the project
  knows how to build, required or optional. Make builds that file and then reads
  every makefile again from the top, so an include below it is read a second
  time, with whatever the rebuilt file defines, and what it reads on the first
  pass is not what Make ends up with. An include that finds no file at all is
  still reported, since Make stops there before it rebuilds anything.
- Everything about a variable's value holds only for a file Make reads on its
  own, meaning one named `Makefile`, `makefile` or `GNUmakefile`. A file under
  any other name may be a fragment something includes, in which case the caller
  has already run: a name defined below the include may hold the caller's value
  there, and one the file never defines certainly does. Checking such a file by
  name reports only the includes whose path the file states outright. Checking
  the project it belongs to reads the caller first, and reports it in full.
- Include expressions blocked for any other reason are left to MK210 when that
  rule is enabled. MK210 also reports the two cases above, because Rumk does not
  follow an include it could not expand.

## Basis

This rule models GNU Make's
[Makefile inclusion and search behavior][gnu-include].
