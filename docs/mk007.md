# MK007 - Path Could Not Be Read

## What this rule does

Reports a path that Rumk could not read as written, instead of stopping the
whole run there:

- A file that cannot be opened or read (missing permissions, an I/O error) is
  reported at line 1 as an error. Nothing in the file is checked.
- A directory that cannot be searched is reported at line 1 as an error, because
  it may hide Makefiles that were never checked.
- A path whose type Rumk may not even ask about, such as one below a directory
  it cannot search, is reported at line 1 as an error without naming it a file
  or a directory.
- A file that is not valid UTF-8 is reported as a warning at the first invalid
  byte. Rumk lints it with every invalid sequence replaced by U+FFFD, disables
  every fix in it, and never writes the replaced content back.

The remaining files are checked normally, and an unreadable directory does not
count towards the files checked.

## Why this matters

A linter that aborts on the first unreadable path hides every finding in the
files after it, and a run that silently skips such a path reports success for
something it never checked. Reporting the path as a diagnostic keeps the run
going and keeps the exit code honest.

Writing a lossy decode back would replace the invalid bytes with U+FFFD, a
change no fix asked for. That is why fixes are disabled in such a file.

## Examples

```text
vendor/Makefile:1:1: [MK007] File could not be read: Permission denied (os error 13)
build:1:1: [MK007] Directory could not be read, so any Makefile in it was missed: Permission denied (os error 13)
locked/Makefile:1:1: [MK007] Path could not be read: Permission denied (os error 13)
legacy.mk:3:12: [MK007] File is not valid UTF-8; invalid bytes were replaced before linting and fixes are disabled
```

## Configuration

MK007 is enabled by default and has no rule-specific options.

An unreadable file or directory at error severity fails every command with exit
code 1, regardless of `--fail-on`, because nothing behind that path was checked.
Lower the severity to let such a path pass:

```toml
[MK007]
severity = "warning"
```

A file that is not valid UTF-8 was linted, so its diagnostic follows `--fail-on`
like any other.

When MK007 is disabled, an unreadable file or directory is skipped with a warning
on standard error (suppressed by `--silent`) and does not affect the exit code,
and a file that is not valid UTF-8 is linted lossily without a diagnostic.
Ignoring MK007 for a path through `[per-file-ignores]` skips it the same way,
without the warning.

An unreadable path that `exclude` matches is not reported at all, and neither is
a directory whose contents are all excluded by a `dir/**` pattern: the run would
have checked nothing behind it either way.

## Automatic fixes

MK007 does not offer fixes. Fixes for every other rule are disabled in a file
that is not valid UTF-8.

## Special cases

- A file pulled in by an `include` directive that cannot be read is reported by
  MK206 at the `include` line, not by MK007. An include that is only invalid
  UTF-8 can be read: it is analyzed with the invalid bytes replaced, and MK007
  reports it when that file is itself checked.
- Inline suppressions such as `# rumk-disable MK007` apply to the UTF-8
  warning, which sits inside the file; an unreadable file has no lines to hold
  one.
- `include` does not silence an unreadable path the way `exclude` does. A
  pattern such as `Makefile` or `*.mk` names files in every directory, so an
  unreadable directory can still hide a file the run would have checked.
- A path passed on the command line that does not exist is still a tool error
  with exit code 2. A Makefile whose metadata Rumk may not read, such as one
  below a directory it cannot search, is reported by MK007 instead.

## Basis

Modeled on Ruff's `E902` (`io-error`), which reports a path that cannot be read
as a diagnostic so that one bad path does not abort the run.

- [Ruff rule io-error (E902)][ruff-e902]
