# MK208 - Define Static Graph Variables

## What this rule does

Reports statically named variable references in assignments and build-graph
declarations when they do not resolve to a project definition, a GNU Make
built-in, or a configured predefined variable, and when they resolve only after
Make has already read them.

This rule is opt-in.

## Why this matters

A misspelled variable in a target, prerequisite, include, or assignment often
expands to an empty string and silently changes the build graph. Checking only
static graph contexts catches these mistakes without treating normal recipe
parameters as errors. A name that is defined, but below the `:=` assignment that
reads it, expands to an empty string in exactly the same way, and reads as
correct because the definition is right there on the page.

## Examples

### Correct

```makefile
BUILD_DIR := build
$(BUILD_DIR)/app: main.o
```

### Incorrect

```makefile
BUILD_DIR := build
$(BUIDL_DIR)/app: main.o
```

A `:=` assignment is also incorrect when it reads a variable the project defines
further down. GNU Make expands the value where it is written, so `OUT` below is
`/app`, and the definition on the second line never reaches it:

```makefile
OUT := $(BUILD_DIR)/app
BUILD_DIR := build
```

## Configuration

Enable MK208 and declare values supplied outside the Makefile:

```toml
[global]
predefined-variables = { TARGET = "release" }

[MK208]
enabled = true
```

If the name is intentionally supplied by callers but its value is unknown, use
an exact name declaration instead:

```toml
[MK208]
enabled = true
external-variables = ["TESTS", "EXTRA_TESTFLAGS"]
```

This list defaults to empty. Names are case-sensitive literals, not patterns:
`TESTS` does not silence `TSET` or `tests`. Empty names, whitespace and Make
metacharacters are rejected. Duplicate names have no additional effect. The
legacy `[rules.MK208.options]` table also accepts `external-variables`.

This option suppresses only MK208's undefined-name warning. It supplies no
value, changes no condition or prerequisite expansion, and does not suppress
local read-before-definition warnings. Use `global.predefined-variables` when
you know the value and want Rumk to evaluate with it. Do not declare a name
merely to silence an unexplained warning: it could be a typo, an unresolved
include, or a scope-analysis limitation.

## Automatic fixes

MK208 does not offer an automatic fix. A name may be misspelled, omitted, or
intentionally supplied by the caller.

## Special cases

- Recipes and deferred `define` bodies are excluded because external and shell
  variables are normal there.
- GNU Make built-in variables such as `MAKE`, `CURDIR`, and `CC` are known.
- References in conditionally indeterminate branches are excluded.
- Dynamic variable names are not guessed.
- A value Make expands only when it is used, such as one written with `=`, reads
  the definition further down, so it is not reported.
- A definition that writes nothing, such as `BUILD_DIR :=`, leaves a reading
  above it worth exactly what a reading below it is worth, and one that only
  reads the name back and writes it again, such as
  `BUILD_DIR := $(strip $(BUILD_DIR))`, passes along whatever the caller
  supplied. Neither is a definition a reading above it should have waited for.
- A definition Make may never read, such as one inside an indeterminate
  conditional, is not one this reports. The name is instead reported as having
  no definition, so the mistake is named once.
- An include read before the definition it needs is MK206's, which is enabled by
  default and says which file Make reads instead.

## Basis

Variable expansion follows GNU Make's
[variable reference syntax][gnu-reference]. The diagnostic policy is a
conservative Rumk convention and is opt-in because Make permits callers to
supply arbitrary variables.

[gnu-reference]: https://www.gnu.org/software/make/manual/html_node/Reference.html
